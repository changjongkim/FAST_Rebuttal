## 1. Can you provide a controlled breakdown separating the gains of your storage design from faster networking and data compression? How does block size affect improvements?

For transport, we ran CASCADE with MPI over TCP on Slingshot-11, the transport of the peer baselines. In the weak-scaling setup of Figure 14 with 64K prefixes, the TTFT of CASCADE over TCP remained 1.09s to 1.12s on 2, 4, and 8 nodes, against 0.92s to 1.21s over RDMA. On the same TCP, Mooncake rose from 1.37s to 9.31s, and LMCache (P2P) took 2.71s to 4.04s. CASCADE used one 16-token vLLM page per block against the 256-token chunks of the peers. Since the 64K prefixes align with both sizes and all three systems reused about 99% of prompt tokens, the gap does not come from prefix matching. Over TCP, the added time appeared in KV Retrieval and Scheduler Queue, and KV Lookup took only 0.12s. The peers rely on centralized coordination to locate each block, whereas CASCADE resolves locations in its local Global Shard Index replica. Thus, CASCADE outperforms both peers on the same transport, and RDMA further shortens KV Retrieval. For compression, disabling INT8 in the trace-driven evaluation lowered retrieval latency at every block size, from 47ms to 19ms for 160MB blocks on 4 nodes. As a result, the low retrieval latency of CASCADE does not depend on compression. Without compression, retrieval latency grew in proportion to block size, at 5ms, 10ms, 19ms, and 38ms for 40, 80, 160, and 320MB blocks on 4 nodes.

## 2. Does lossy compression affect output quality on long-document tasks, and how does the system impact token generation speed and full request time?

CASCADE compresses only the block copies outside GPU HBM, and decoding reads the decompressed FP16 blocks in GPU HBM (Section 3.3). Thus, compression changes the stored KV values but not the decoding path. With one scale and zero point per layer for keys and for values, INT8 bounds the error of each value to 1/510 of its range. A separate range per layer prevents outlier keys of one layer from enlarging the quantization step of other layers. On 2 and 4 nodes, one scale per block lowered the F1 score from 39.9 to 37.9. With per-layer INT8 on every retrieved block, CASCADE scored an F1 of 40.0 against 40.3 for vLLM GPU on 280 questions from six English LongBench question answering tasks over 2 to 8 nodes. For token generation, we ran four concurrent requests per node with 64K prefixes and 128 output tokens on 2 to 8 nodes. CASCADE generated tokens up to 10% faster than vLLM GPU, at 48ms to 50ms against 53ms per token. vLLM GPU is slower because its decoding steps also process the prefill of recomputed prompts, and its request that decoded after all prefills took 46ms per token. Since CASCADE retrieved 99.9% of the prompt tokens, its median TTFT was 14s to 17s against 55s to 57s. With about 6s of decoding in both systems, the full request time was about 3 times shorter, at 20s to 22s against 62s to 64s.

## 3. How does the system reuse partial chunks on early conversation divergence and reclaim obsolete data in shared persistent files?

CASCADE reuses a prefix up to the last complete block before divergence. Each Block ID is a SHA-256 hash of the tokens of a block and the preceding Block ID, so identical prefixes produce the same Block ID sequence until divergence. The block size sets this granularity, with 512 and 1024 KV pairs in the trace-driven evaluation and one 16-token page in our vLLM integration, which recomputes at most 15 shared tokens at a divergence. In our runs, requests that diverged after a 64K shared prefix reused 99.9% of their prompt tokens.
For each block on Lustre, Location Metadata records the aggregate file and the offset. When Eviction Manager purges a block, CASCADE invalidates its Global Shard Index entry. CASCADE can then count the valid blocks of each aggregate file and delete the file once the count drops to zero and Metadata Sync has propagated the invalidations. File deletion rewrites no valid block, and a partially valid file remains until its last valid block is invalidated. The current prototype does not count valid blocks per file.

## 4. How does cross-machine coordination handle server failures or dynamic scaling?

CASCADE targets LLM inference on HPC systems, where the nodes of an allocation remain fixed during execution. Thus, our paper did not consider node failures or dynamic scaling within an allocation. However, the decentralized Global Shard Index of CASCADE can support both without a central metadata service.
Each Location Metadata entry identifies the node that stores a block. If the MPI runtime supports communicator recovery, the remaining nodes can rebuild the MPI communicator after a node failure and invalidate the entries of the failed node. Later lookups of the invalidated blocks become cache misses, and CASCADE recomputes the KV blocks from their token sequences. With rebuilt RDMA Windows, the remaining nodes can then continue retrieval.
For dynamic scaling, a new node can receive the current Global Shard Index and take part in the periodic Metadata Sync. Since Location Metadata records the location of each block, a new mapping of Block IDs to shards rebuilds only the index and moves no stored block. Dynamic scaling also requires rebuilding the MPI communicator and RDMA Windows. Thus, Global Shard Index supports both node failures and dynamic scaling.

## 5. Sharing KV Cache blocks across tenants may introduce an information channel in between tenants, so information can be leaked (for example, fast TTFT for a never-used before prompt suggests to the attacker that a co-tenant used the same prompt before). Is salting optional in your HPC environment

Yes, salting is optional and set per request. Since each Block ID chains from the first block, a salt in the first block changes every later Block ID of the request. As a result, requests with different salts cannot share cached prefixes, which removes the timing channel of cross-tenant cache hits. With one shared salt, four concurrent requests per node, and one output token, 64K runs on 2 and 4 nodes reused 99.9% of prompt tokens at a TTFT of 7.5s to 7.7s. Requests with another tenant's salt reused no cached prefix block at a TTFT of 48.4s to 48.7s, equal to recomputation, so a prefix cached by another tenant shows no timing difference. One salt per tenant retains deduplication within each tenant, and our vLLM integration sets it through the cache salt of vLLM.

## 6. Please respond to other questions posted in the reviews.

**Global Shard Index.** (RA, RB, RD) Every node of CASCADE stores a full replica of Global Shard Index in host DRAM and resolves block locations locally. The node that stores a block writes its entry, and Metadata Sync copies the entry to every replica. Shards are logical partitions of each replica keyed by GPU ID, so lookups and Index Merger on different shards proceed in parallel. Location Metadata records the tier of each block, including Lustre, and the replica itself is not persistent. Dedup Map filters PUTs, and Global Shard Index resolves locations for retrieval. Before block allocation, Dedup Coordinator checks only whether any copy exists, which changes at creation and full eviction from all nodes, whereas a Location Metadata entry changes at every block movement. As a result, the PUT check remains valid during block movement. Dedup Map adds about 0.3µs per merged delta to Metadata Sync, off the retrieval path, and the deduplication that relies on it avoids 57 to 66% of block writes (Table 3).

**Consistency and metadata scaling.** (RA, RB) Since concurrent PUTs of the same Block ID produce equivalent copies, Metadata Sync needs no synchronous conflict resolution. Each entry names its node, and an invalidation removes the entry only while it names the invalidating node. A node publishes a location only after the block is stored in Shadow Copy Buffer (Algorithm 1). After an RDMA READ, the reader matches the Block ID stored with the block against the requested one and the payload against the checksum recorded for that Block ID (Section 3.3). A read of a replaced slot, even a partially overwritten one, fails validation. CASCADE then recomputes the block, so stale metadata costs cache hits but not the correctness of an accepted KV block. In a metadata stress test with 4KB blocks on 4 nodes, Metadata Sync took at most 41ms and 569ms with 10K and 100K new blocks per node per interval. At 100K blocks per second per node, the two points equal intervals of 100ms and 1000ms, so each sync finished within its interval. MPI_Allgatherv of the same deltas took at most 5.5ms and 51ms, so local processing, not the network, dominated each sync. Before each sync, reads of the new blocks of another node missed, and all 72,000 reads after the sync hit with 0 Block ID mismatches. Thus, a longer sync converts more cross-node reuses into recomputation, but lookups remain local (Section 3.2). Our 4-node end-to-end runs created fewer than 100 blocks per node per interval, far below the stress test.

**Workload and statistics.** (RA, RB, RD) The end-to-end evaluation routes requests to prefixes cached on other nodes to isolate cross-node reuse rather than to model cache-aware routing. In the reported runs, CASCADE, Mooncake, and LMCache (P2P) achieve hit rates of approximately 99%, so Figure 16 attributes the TTFT gap to KV Lookup, KV Retrieval, GPU Transfer, Scheduler Queue, and Prefill. Figure 7 scales the requests with the node count for weak scaling and fixes 128 requests for strong scaling. In three or more repeated runs at two or more nodes, the coefficient of variation of TTFT is at most 11% for CASCADE and Mooncake, small relative to their TTFT gap.
