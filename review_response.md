## 3. How does the system reuse partial chunks on early conversation divergence and reclaim obsolete data in shared persistent files?

CASCADE reuses a prefix up to the last complete block before divergence. Each Block ID is a SHA-256 hash of the tokens of a block and the preceding Block ID, so identical prefixes produce the same Block ID sequence until divergence. Only the tokens after the last shared block are then recomputed. A smaller block provides finer reuse at the cost of more 80-byte Location Metadata entries.
For each block on the PFS, Location Metadata records the aggregate file and the offset. When Eviction Manager purges a block, CASCADE invalidates its Global Shard Index entry. CASCADE can then count the valid blocks of each aggregate file and delete the file once the count drops to zero and Metadata Sync has propagated the invalidations. File deletion rewrites no valid block. The current prototype does not count valid blocks per file, and the count requires no change to Global Shard Index.

## 4. How does cross-machine coordination handle server failures or dynamic scaling?

CASCADE targets LLM inference on HPC systems, where the nodes of an allocation remain fixed during execution. Thus, our paper did not consider node failures or dynamic scaling within an allocation. However, the decentralized Global Shard Index of CASCADE can support both without a central metadata service.
Each Location Metadata entry identifies the node that stores a block. After a node failure, the remaining nodes can rebuild the MPI communicator and invalidate the entries of the failed node. Later lookups of the invalidated blocks become cache misses, and CASCADE recomputes the KV blocks from their token sequences. With rebuilt RDMA Windows, the remaining nodes can then continue retrieval.
For dynamic scaling, a new node can receive the current Global Shard Index and take part in the periodic Metadata Sync. Since Location Metadata records the location of each block, a new mapping of Block IDs to shards moves no stored block. Dynamic scaling also requires rebuilding the MPI communicator and RDMA Windows. Thus, Global Shard Index provides the metadata path for both cases.

## 5. Sharing KV Cache blocks across tenants may introduce an information channel in between tenants, so information can be leaked (for example, fast TTFT for a never-used before prompt suggests to the attacker that a co-tenant used the same prompt before). Is salting optional in your HPC environment

Yes, salting is optional and set per request. Since each Block ID chains from the first block of a request, a salt in the hash of the first block changes every later Block ID of the request. As a result, requests with different salts cannot share cached prefixes, which removes cache hits as an information channel between tenants. A single-user allocation disables salting to maximize deduplication, and a multi-tenant service assigns one salt per tenant, which retains deduplication within each tenant. Our vLLM integration already supports per-tenant salts through the cache salt of vLLM in each block hash.

## 6. Please respond to other questions posted in the reviews.

**Global Shard Index.** (RA, RB, RD) Mooncake and LMCache (P2P) resolve each block location through a central service before an RDMA transfer. In contrast, CASCADE resolves the location from a full replica of Global Shard Index in host DRAM of every node. Since a Block ID identifies its KV content, any copy is correct, and the replicas need no coordination. The node that stores a block writes its entry, and Metadata Sync copies the entry to every replica. Shards are logical partitions of each replica keyed by GPU ID, so lookups and Index Merger on different shards proceed in parallel. Location Metadata records the tier of each block, including Lustre, and the replica itself is not persistent. Dedup Map tracks only the existence of a block, which changes at creation and full eviction, whereas Location Metadata changes at every block movement.

**Consistency and metadata scaling.** (RA, RB) Content addressing removes metadata conflicts, since concurrent PUTs of the same Block ID produce equivalent copies. A node publishes a location only after the block is stored in Shadow Copy Buffer (Algorithm 1). When a new shadow copy replaces an evicted block, an RDMA READ on the old location, even during the replacement, fails Block ID or checksum validation (Section 3.3). CASCADE then recomputes the block, so stale metadata costs cache hits but not the correctness of an accepted KV block. On 4 nodes, Metadata Sync took at most 2.4, 41, and 569 ms with 1K, 10K, and 100K new blocks per node per interval. The three points equal intervals of 10, 100, and 1000 ms at 100K blocks per second, and our 4-node end-to-end runs created fewer than 100 blocks per node per interval. MPI_Allgatherv of the same deltas took at most 0.2, 5.5, and 51 ms, so Index Merger on the host CPU dominated each sync. A longer sync converts more cross-node reuses into recomputation without blocking lookups on the local replica (Section 3.2). Before each sync, reads of the new blocks of another node missed, and all 72,000 reads after the sync hit with 0 Block ID mismatches.

**Workload and statistics.** (RA, RB, RD) The end-to-end evaluation routes requests to prefixes cached on other nodes to isolate cross-node reuse. In the reported runs, CASCADE, Mooncake, and LMCache (P2P) achieve hit rates of approximately 99%, so Figure 16 attributes the TTFT gap to KV lookup, retrieval, GPU transfer, scheduler queueing, and prefill. Figure 7 evaluates weak and strong scaling with 160MB and 320MB blocks, and strong scaling fixes 128 requests. For P99.9, each rank in Figure 8 issues 300 to 500 reads. Across three or more repeated end-to-end runs at two or more nodes, the coefficient of variation of TTFT is at most 11% for CASCADE and Mooncake.
