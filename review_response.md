## 1. Can you provide a controlled breakdown separating the gains of your storage design from faster networking and data compression? How does block size affect improvements?

For transport, we ran CASCADE with MPI over TCP on Slingshot-11, the transport of the peer baselines, with every other setting unchanged. On 2, 4, and 8 nodes with 64K prefixes, TTFT rose from 2.8 to 3.0 s over RDMA to 10.7, 7.0, and 6.9 s over TCP. In the breakdown of Figure 16, the added time appeared in KV Retrieval and Scheduler Queue, while KV Lookup and Prefill remained unchanged. Metadata Sync over TCP also took at most 68 ms for 10K new blocks per node per interval. Thus, RDMA shortens KV Retrieval and the queueing behind it, while the metadata path and tier management of CASCADE remain the same over both transports. For compression, the trace-driven evaluation of Figure 7 without INT8 compression lowered retrieval latency at every block size, from 47 to 19 ms for 160MB blocks on 4 nodes. As a result, the low retrieval latency of CASCADE does not depend on compression. Without compression, retrieval latency grew in proportion to block size, at 5, 10, 19, and 38 ms for 40, 80, 160, and 320MB blocks on 4 nodes. Data movement, not a fixed cost per block, sets the latency at these sizes.

## 2. Does lossy compression affect output quality on long-document tasks, and how does the system impact token generation speed and full request time?

CASCADE compresses only the block copies outside GPU HBM, and decoding reads the decompressed FP16 blocks in GPU HBM (Section 3.3). Thus, compression changes the stored KV values but not the decoding path. With one scale and zero point per layer for keys and for values, INT8 bounds the error of each value to 1/510 of its range. Since each layer has its own range, outlier keys in one layer do not coarsen other layers. With this INT8 on every retrieved block, CASCADE scored an F1 of 39.9 on 120 questions from the six English question answering tasks of LongBench over 2 and 4 nodes, equal to vLLM GPU. One scale per block scored 37.9, and CASCADE without compression scored 39.3. For decoding, both systems read the KV cache in GPU HBM, and CASCADE completes PUT operations off the decoding path. With 64K prefixes and 128 output tokens on 2 to 8 nodes, the median time per generated token was 48 to 50 ms with CASCADE and 53 ms with vLLM GPU. vLLM GPU generates tokens more slowly because its decoding steps also process the prefill of recomputed prompts, and its request that decoded after all prefills took 46 ms per token. Since CASCADE retrieved 99.9% of the prompt tokens, the median TTFT fell from 55 to 57 s to 14 to 17 s. Decoding added about 6 s to both systems, so the full request time fell from 62 to 64 s to 20 to 22 s.

## 3. How does the system reuse partial chunks on early conversation divergence and reclaim obsolete data in shared persistent files?

CASCADE reuses a prefix up to the last complete block before divergence. Each Block ID is a SHA-256 hash of the tokens of a block and the preceding Block ID, so identical prefixes produce the same Block ID sequence until divergence. Only the tokens after the last shared block are then recomputed. A smaller block provides finer reuse at the cost of more 80-byte Location Metadata entries.
For each block on the PFS, Location Metadata records the aggregate file and the offset. When Eviction Manager purges a block, CASCADE invalidates its Global Shard Index entry. CASCADE can then count the valid blocks of each aggregate file and delete the file once the count drops to zero and Metadata Sync has propagated the invalidations. File deletion rewrites no valid block, and a partially valid file remains until its last valid block is invalidated. The current prototype does not count valid blocks per file, and the count derives from the invalidations that Metadata Sync already propagates.

## 4. How does cross-machine coordination handle server failures or dynamic scaling?

CASCADE targets LLM inference on HPC systems, where the nodes of an allocation remain fixed during execution. Thus, our paper did not consider node failures or dynamic scaling within an allocation. However, the decentralized Global Shard Index of CASCADE can support both without a central metadata service.
Each Location Metadata entry identifies the node that stores a block. If the MPI runtime supports communicator recovery, the remaining nodes can rebuild the MPI communicator after a node failure and invalidate the entries of the failed node. Later lookups of the invalidated blocks become cache misses, and CASCADE recomputes the KV blocks from their token sequences. With rebuilt RDMA Windows, the remaining nodes can then continue retrieval.
For dynamic scaling, a new node can receive the current Global Shard Index and take part in the periodic Metadata Sync. Since Location Metadata records the location of each block, a new mapping of Block IDs to shards rebuilds only the index and moves no stored block. Dynamic scaling also requires rebuilding the MPI communicator and RDMA Windows. Thus, Global Shard Index provides the metadata path for both cases.

## 5. Sharing KV Cache blocks across tenants may introduce an information channel in between tenants, so information can be leaked (for example, fast TTFT for a never-used before prompt suggests to the attacker that a co-tenant used the same prompt before). Is salting optional in your HPC environment

Yes, salting is optional and set per request. Since each Block ID chains from the first block of a request, a salt in the hash of the first block changes every later Block ID of the request. As a result, requests with different salts cannot share cached prefixes, which removes the timing channel of cross-tenant cache hits. A single-user allocation disables salting to maximize deduplication, and a multi-tenant service assigns one salt per tenant, which retains deduplication within each tenant. Our vLLM integration already supports per-tenant salts through the cache salt of vLLM in each block hash.

## 6. Please respond to other questions posted in the reviews.

**Global Shard Index.** (RA, RB, RD) Mooncake and LMCache (P2P) resolve each block location through a central service before a peer transfer. In contrast, CASCADE resolves the location from a full replica of Global Shard Index in host DRAM of every node. The node that stores a block writes its entry, and Metadata Sync copies the entry to every replica. Shards are logical partitions of each replica keyed by GPU ID, so lookups and Index Merger on different shards proceed in parallel. Location Metadata records the tier of each block, including Lustre, and the replica itself is not persistent. Dedup Map filters PUTs, and Global Shard Index resolves locations for retrieval. Before block allocation, Dedup Coordinator checks only whether any copy exists, which changes at creation and full eviction from all nodes, whereas a Location Metadata entry changes at every block movement. As a result, the PUT check remains valid during block movement, at the cost of one flag per block in every replica.

**Consistency and metadata scaling.** (RA, RB) Since concurrent PUTs of the same Block ID produce equivalent copies, Metadata Sync needs no synchronous conflict resolution. Each entry names its node, and an invalidation removes the entry only while it names the invalidating node. A node publishes a location only after the block is stored in Shadow Copy Buffer (Algorithm 1). After an RDMA READ, the reader checks the Block ID stored with the block and the payload checksum (Section 3.3), so a read of a replaced slot fails validation. CASCADE then recomputes the block, so stale metadata costs cache hits but not the correctness of an accepted KV block. In a metadata stress test with 4 KB blocks on 4 nodes, Metadata Sync took at most 41 and 569 ms with 10K and 100K new blocks per node per interval. At 100K blocks per second per node, the two points equal intervals of 100 and 1000 ms, so each sync finished within its interval. MPI_Allgatherv of the same deltas took at most 5.5 and 51 ms, so local processing, not the network, dominated each sync. Before each sync, reads of the new blocks of another node missed, and all 72,000 reads after the sync hit with 0 Block ID mismatches. Thus, a longer sync converts more cross-node reuses into recomputation, but lookups remain local (Section 3.2). Our 4-node end-to-end runs created fewer than 100 blocks per node per interval, far below the stress test.

**Workload and statistics.** (RA, RB, RD) The end-to-end evaluation routes requests to prefixes cached on other nodes to isolate cross-node reuse rather than to model cache-aware routing. In the reported runs, CASCADE, Mooncake, and LMCache (P2P) achieve hit rates of approximately 99%, so Figure 16 attributes the TTFT gap to KV lookup, retrieval, GPU transfer, scheduler queueing, and prefill. Figure 7 scales the requests with the node count for weak scaling and fixes 128 requests for strong scaling. For P99.9, Figure 8 pools the reads of all ranks, up to 19,200 reads at 64 nodes. In three or more repeated runs at two or more nodes, the coefficient of variation of TTFT is at most 11% for CASCADE and Mooncake, small relative to their TTFT gap.
