## 3. How does the system reuse partial chunks on early conversation divergence and reclaim obsolete data in shared persistent files?
CASCADE reuses a prefix up to the last complete block before divergence. Each Block ID is a SHA-256 hash of the tokens of a block and the preceding Block ID. As a result, identical prefixes produce the same Block ID sequence until divergence, and only the tokens after the last shared block are recomputed. The reuse granularity follows the block size. A smaller block size provides finer reuse at the cost of more Location Metadata entries, each of which requires only 80 bytes.
When Eviction Manager purges a block, CASCADE invalidates the Global Shard Index entry of the block, and these invalidations can support the reclamation of aggregate files on the PFS. For each block on the PFS, CASCADE also records the aggregate file and the offset. CASCADE can count the valid entries of each aggregate file and delete the file once the count drops to zero and Metadata Sync has propagated the invalidations to every replica. File deletion rewrites no valid block. Space of invalid entries in a partially valid file remains until the file has no valid entry. The current prototype does not count valid entries per file, and we will add the file deletion in the revision.

## 4. How does cross-machine coordination handle server failures or dynamic scaling?

CASCADE targets fixed-size MPI jobs on HPC systems, where the node set of a job does not change during execution. Thus, our paper did not consider node failures or dynamic scaling within a job. However, the decentralized Global Shard Index of CASCADE can support both without a central metadata service.
Each Location Metadata entry identifies the node that stores a block. After a node fails and the MPI world is rebuilt with the remaining nodes, the remaining nodes can invalidate the entries of the failed node. Later lookups of the invalidated blocks become cache misses, and CASCADE recomputes the KV blocks from their token sequences. With rebuilt RDMA Windows, the remaining nodes can continue lookup and retrieval through the updated Global Shard Index. The requests on the failed node are outside the scope of the current prototype.
For dynamic scaling, a new node can receive the current Global Shard Index and take part in the periodic Metadata Sync. Since Location Metadata records the location of each block, a new mapping of Block IDs to shards moves no stored block. Dynamic scaling still requires rebuilding the MPI world and the RDMA Windows. Thus, Global Shard Index provides the metadata path for both cases, and we will describe the design in the revision.

## 5. Sharing KV Cache blocks across tenants may introduce an information channel in between tenants, so information can be leaked (for example, fast TTFT for a never-used before prompt suggests to the attacker that a co-tenant used the same prompt before). Is salting optional in your HPC environment

Yes, salting is optional and set per request. Since each Block ID chains from the first block of a request, a salt in the hash of the first block changes every later Block ID of the request. As a result, requests with different salts cannot share cached prefixes, which removes cache hits as an information channel between tenants. Within one salt, Global Shard Index and Dedup Map operate unchanged and deduplicate the shared prefixes of the tenant. A single-user allocation disables salting to maximize deduplication, and a multi-tenant service assigns one salt per tenant. Our vLLM integration already supports per-tenant salts, since its Block IDs derive from the vLLM block hash with the per-request cache salt.

## 6. Please respond to other questions posted in the reviews.

**Global Shard Index.** (RA, RB, RD) RDMA alone does not remove the location lookup, and Mooncake and LMCache (P2P) resolve each location through a central service before a transfer. CASCADE eliminates the per-request central lookup. Since a Block ID identifies its KV content, any copy of a block is correct. Thus, every node stores a full replica of Global Shard Index in host DRAM and resolves a remote location locally before one one-sided read. The node that stores a block writes its entry, and Metadata Sync copies the entry to every replica. Shards are logical partitions keyed by GPU ID, so lookups and Index Merger on different shards proceed in parallel. Location Metadata records the tier of each block, including Lustre. Each replica is not persistent, whereas Lustre persists the KV blocks evicted from DRAM. Dedup Map tracks only the existence of a block, which changes at creation and full eviction, while Location Metadata changes at every tier movement.

**Consistency and metadata scaling.** (RA, RB) Content addressing makes eventual consistency safe for KV cache. Concurrent PUTs of the same Block ID produce equivalent copies, so any location is correct and metadata conflicts need no resolution. A node publishes a location only after the block is stored in Shadow Copy Buffer (Algorithm 1). After eviction or DRAM slot reuse, an RDMA READ on the old location, including a read of a partially overwritten slot, fails Block ID or checksum validation (Section 3.3). CASCADE then rejects the block and recomputes it as a cache miss. Thus, staleness costs cache hits before the next Metadata Sync, not the correctness of an accepted KV block. On 4 nodes, Metadata Sync took at most 2.4, 41, and 569 ms with 1K, 10K, and 100K new blocks per node per interval. At 100K new blocks per second per node, the three points correspond to intervals of 10, 100, and 1000 ms, and our 4-node E2E runs created fewer than 100 blocks per node per interval. An Allgatherv of the same deltas took at most 0.2, 5.5, and 51 ms, so Index Merger on the host CPU dominated the sync. A longer sync extends staleness and converts more cross-node reuses into recomputation, while lookups remain reads of the local replica (Section 3.2). Reads of blocks from the current interval missed before the sync, and all 72,000 reads after the sync hit with 0 Block ID mismatches.



**Workload and statistics. (RA, RB, RD)** The end-to-end evaluation routes requests to prefixes cached on other nodes to isolate cross-node reuse. In the reported runs, CASCADE, Mooncake, and LMCache (P2P) achieve approximately 99% token hit rates.
